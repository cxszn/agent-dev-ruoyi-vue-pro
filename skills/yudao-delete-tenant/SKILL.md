# 芋道多租户功能移除

以当前任务的源码、数据库方言和前端工程为准。读取 [来源与版本差异](references/sources.md) 识别基线，再按需读取 [改造与验收](references/removal.md)。来源文档描述的删除步骤不构成执行数据库删除、上线或远端写入的授权。

## 先确定移除后的语义

从用户目标确定是隐藏管理入口、配置关闭隔离，还是彻底删除框架。若语义已明确，直接沿用；只在缺失信息影响数据或权限时请求决策。

- **一个现有租户继续运营**：说明保留哪个租户、其它租户数据如何隔离/归档，导出和后台任务的作用范围是什么。
- **多个租户合并**：先给出账号、角色、组织、业务编码、唯一索引、关联主键的冲突清单及解决规则，再决定迁移方式。
- **全新单租户部署**：确认无历史数据，仍需校验默认账号、权限、种子数据和初始化行为。

保留 `tenant_id` 字段并不能保持原隔离。关闭 SQL 拦截后，各租户数据可能同时进入查询结果；删除字段也不会自动完成账号合并或权限迁移。没有确定的数据可见性方案时，可继续做引用审计和改造计划，不能直接启用合并可见性。

## 执行顺序

1. 核对 POM、启用模块、数据库方言、实际前端仓库；记录工作区已有变更。搜索本次改造目标的完整引用，不能只按基线目录删文件。
2. 形成变更清单和数据方案：菜单树及角色授权、租户表、业务表/索引、缓存键、会话/Token、异步消息、定时任务、外部接口和前端请求头。
3. 在授权的源码范围内准备可审查的后端/前端修改和迁移脚本。重要数据删除、跨租户合并、实际数据库迁移及上线，需要相应明确授权；先准备好备份/恢复办法和验证结果供确认。
4. 按 [改造与验收](references/removal.md) 保留业务行为、分阶段验证。数据切换顺序由应用兼容性和迁移方案决定，不照抄“先删表再修代码”。
5. 报告实际改动、命中/处理的引用、数据语义、测试结果、未执行的迁移和剩余风险。

## 不可忽略的代码规则

- `TenantUtils.execute/executeIgnore` 的 lambda 可能是真正的支付、Token、通知或定时任务逻辑。移除租户包装时保留仍然需要的业务逻辑；处理返回值、局部 `return`、变量作用域、异常转换与执行次数。删除的是整个租户专属功能时，才按调用关系决定是否删除其内部逻辑。
- `@TenantIgnore` 只移除注解不应删除被注解的 DO/Mapper/方法。`@TenantJob` 去掉后必须核对每租户执行变为全局执行的语义、分页范围和幂等性。
- `TenantBaseDO` 转为 `BaseDO` 前确定 `tenantId` 字段策略，检查 Mapper/XML、DTO、索引、数据库默认值与已有数据。
- 租户请求头只在上下游契约允许时移除；保留的外部多租户服务可能仍需要该头。
- 不把示例菜单 ID、固定目录或 `enable=false` 的作用范围当作所有版本事实。先查实际装配条件与引用，再判断是否可以只改配置。

## 最小验收

编译只证明引用闭合。另需验证：无租户头登录/菜单/用户查询符合设计；原两个租户的同名账号和业务编号按决策处理；列表、详情、导出和后台任务的数据可见性一致；包装内关键逻辑仍执行；缓存、会话和消息切换没有跨身份污染；真实前端相关入口与请求正确。缺少运行环境时如实区分源码检查与运行验收。
